One row per capability, one column per product. opencode gets two columns because v1 (1.18.31) and v2 (2.0.3) differ
often enough to matter. lootbox means the deployed build (upstream `587a5a1` plus four patches); cells citing the
`.lootbox/` fork say so where the fork differs ([register CODE-01](register/code-mode.md#code-01-the-deployed-lootbox-is-upstream-587a5a1-plus-four-patches-not-the-fork)).
"—" means absent, with the evidence that it is absent. Rows 1–47 are the capability survey; rows 48–52 add v1/v2
differences from the register; group B lists where each product does something better than mcpx, including the
places where that conflicts with mcpx's goal.
The reasoning and nuance for every row are in [register/code-mode.md](register/code-mode.md). Legend and citation
conventions: [README.md](README.md).

## 2.2 What each assumes an MCP server should be

**lootbox.** lootbox treats a server as a long-lived process or endpoint. It connects to every one at daemon start,
keeps one client per server for all callers, and (fork only) pings it to decide whether it is alive
(`.lootbox/src/lib/rpc/managers/mcp_integration_manager.ts:221-222`; `.lootbox/README.md:385-388`). It assumes the
server needs nothing from the client: it declares `capabilities: {}`, so a server that elicits, samples or asks for
roots is refused (`.lootbox/src/lib/external-mcps/mcp_client_manager.ts:150-153`). It assumes a server's catalogue fits
on one `tools/list` page and one `resources/list` page, and that tool names reduce harmlessly to `[A-Za-z0-9_]`
(`.lootbox/src/lib/external-mcps/mcp_schema_fetcher.ts:69`, `:101`, `:152-154`). It assumes a server is stateless enough
to share; the only concession to stateful servers is rewriting a port found in their command-line arguments, in the
fork (`.lootbox/src/lib/rpc/managers/mcp_integration_manager.ts:82-133`). Results are passed through as raw envelopes,
so the script, not lootbox, is expected to understand `content[]` and `isError`
(`.lootbox/src/lib/rpc/execute_mcp.ts:68-72`).

**Cloudflare code mode.** Cloudflare's premise is that "Almost every MCP server is just a wrapper around an existing
traditional API". MCP's value is that it "provides a uniform way to connect to and learn about an API", with
"authorization handled out-of-band" (blog, "But MCP is still useful, because it is uniform" and "What's MCP?"). A server
is therefore a remote, OAuth-authorised HTTP endpoint that the Agent connects to once. The Agents MCP client offers
only `auto`, `streamable-http` and `sse`, no stdio (client, "Transport options"). The server enforces its own
authorisation: "Enforce permissions and any required approval inside upstream tool handlers" (mcpsrv, "Sandbox and
authorization boundary"). The server should describe its tools well enough to generate typed methods, and a large API
should itself be a code-mode server: two tools, `search` and `execute`, at a fixed footprint of about 1,000 tokens
(blog2, "Server‑side Code Mode"; mcpsrv, "Search and execute"). A server's tool names must be unique after
sanitisation, or the connector throws (mcp, step 2). Side-effecting tools should be safe to pause, replay in the same
order and, ideally, revert (how, "Deterministic replay" and "Rollback").

What opencode and mcpx assume of a server is covered in the opencode and process-model registers.
